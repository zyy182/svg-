## 2. 架构方案

采用分层结构，保持终端交互与业务模型分离。具体目录组织将在语言确定后落地。

```text
终端输入
   ↓
CLI 层：读取输入、解析参数、输出帮助与错误
   ↓
应用层：命令分派、执行编辑事务、管理撤销与重做
   ↓
模型层：文档、图形节点、分组节点、属性与结构约束
   ↕
持久化层：读取与校验 SVG、序列化与保存文件
```

### 职责与设计原则

- CLI 层只负责交互，不直接修改图形内部状态。
- 模型层维护唯一 ID、父子关系、绘制顺序和合法属性，不依赖终端或文件系统。
- 分组和图形通过树形结构统一管理；查找、结构显示和子树删除围绕同一文档模型实现。
- 应用层统一处理编辑成功与失败。成功编辑才能进入撤销历史，失败操作必须保留操作前的完整状态。
- 撤销和重做恢复文档内容及节点顺序。读取、新建、保存是否进入历史将在核对课程规则后确定。
- 持久化层负责文件格式与模型之间的转换。文件读取先完成解析与校验，再替换当前文档；保存应防止写入失败破坏现有文件。
- 优先采用足够简单的实现。撤销可以用命令逆操作或文档快照；在最终确定前比较复杂度、正确性和内存成本，不为设计模式额外增加无用类。

### 核心不变量

1. 文档内元素 ID 唯一。
2. 每个非根节点只有一个父节点，分组不能形成环。
3. 树中子节点顺序与 SVG 绘制顺序一致。
4. 数值参数必须合法；尺寸等属性遵守相应图形约束。
5. 命令错误不会留下部分修改。
6. 同一编辑序列撤销再重做后，文档语义与原结果一致。
7. 读写往返保留约定兼容范围内的图形、属性、层级与变换。

## 3. 开发与 Git 提交计划

在实际完成每个阶段并验证后提交，保持各提交有独立、可解释的目的，不伪造时间或补造开发历史。

1. `docs: record requirements and initial architecture`：需求、架构、验收清单。
2. `feat: implement document and shape model`：模型及其约束验证。
3. `feat: implement SVG persistence`：读取、保存及往返验证。
4. `feat: implement editing and history`：编辑、分组与撤销重做。
5. `feat: add interactive command line`：解析、帮助、错误提示与示例。
6. `test: cover integrated workflows and edge cases`：验收场景和发现问题的修复。
7. `docs: complete consistency review and usage guide`：更新文档，使其与代码一致。

实际提交允许按发现的问题调整粒度。Git 提交作者使用用户确认的姓名与邮箱。所有验收通过、课程全文核对完成后，在实际最终提交处创建 `final` 标签，并将代码及标签推送到用户指定的远程仓库。

## 6. 功能完整性与质量保证

采用三类验证：模型单元测试、持久化往返测试、CLI 端到端操作序列。重点覆盖可观察行为及失败后的状态，避免只重复实现细节。

计划验收场景：

1. 新建文档，创建各类图形，保存并再次读取，检查图形、属性与层级。
2. 创建分组及嵌套分组，对图形和分组移动、缩放，检查几何与顺序。
3. 修改属性、删除子树，逐步撤销再重做，比较文档语义。
4. 撤销后执行新编辑，验证旧重做分支清空。
5. 输入未知命令、错误参数、重复 ID、不存在的 ID、非法数值，验证友好报错与原状态保留。
6. 读取不存在的文件、无效 XML 或兼容范围外的 SVG，确认当前文档不被破坏。
7. 保存至不可写路径，确认文件错误能够被解释且不误报成功。
8. 按文档从干净环境启动工程并完成完整示例。
